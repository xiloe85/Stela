# Stela — Architecture

Audited from `tylertms/Stela` at commit `865c48e` (2026-11-16), cloned to
`Stela-audit/`. Every statement below is traceable to a file in this tree.

## 1. What Stela is

Stela is a **UEFI boot application** (`stela.efi`, `x86_64-unknown-uefi`,
`no_std`) that runs an **unmodified arm64 macOS** by:

1. modelling Apple silicon hardware closely enough that macOS's platform
   code accepts it (**it presents as an M2 Mac mini**),
2. **translating arm64e code to x86-64** (AOT + JIT), and
3. **replacing the Apple GPU** with a Metal device implemented in Stela
   itself, backed by a real PC GPU through Mesa.

Point 3 is the part this port touches. There is no Metal driver *inside*
macOS that one could patch: the guest's unchanged Metal framework is routed
into Stela's Metal device, so "an Intel Arc Metal driver" means completing
Stela's Intel stack. That framing is correct and the upstream code is already
shaped for it.

(headers + libdrm_amdgpu), xnu (headers for the guest kext).

## 3. Boot → Metal execution path

```
UEFI firmware
  └─ stela.efi (crates/stela-boot/src/main.rs)
      ├─ firmware/memory map, paging, heap (stela-boot-core)
      ├─ host enumeration: PCI scan (stela-driver-base::bus::pci)
      │     └─ Adapter::discover  (stela-driver-gpu/src/lib.rs)
      │           class 0x03 → Vendor::{Nvidia,Amd,Intel,Other}
      ├─ GpuStack::select(adapter)      (stela-driver-gpu/src/stack.rs)
      │     ├─ NVIDIA → Kernel{nouveau} + metal::nvidia::ADMISSION + NVK
      │     ├─ AMD    → Kernel{amdgpu}  + metal::amd::ADMISSION    + (RADV: none yet)
      │     └─ INTEL  → Kernel{xe}      + metal::intel::ADMISSION  + (ANV: none yet)
      ├─ engine/gpu.rs: bring up the freestanding Linux environment,
      │     register the kernel drivers built into the image, let Linux
      │     match each PCI function against the drivers' own ID tables
      ├─ guest boots: arm64 macOS, translated by stela-compiler/JIT
      ├─ StelaGPU.kext (guest side, generated by `cargo xtask guest`)
      │     receives Metal calls through a call gate (stela-contracts)
      └─ Stela Metal device (crates/stela-driver-gpu/src/metal/)
            ├─ capability gate: capabilities.rs (Vulkan ∧ AIR compiler ∧ implementation)
            ├─ command encoders → internal Vulkan boundary (metal/vulkan/)
            └─ native backend (metal/native.rs) → linked Mesa Vulkan driver
                  (NVK / ANV / RADV), which programs the real GPU through the
                  kernel driver running inside Stela's Linux environment
```

The key factoring: **the Metal layer is vendor-agnostic**. It speaks an
internal Vulkan boundary; a vendor contributes only *data* through `GpuStack`
(kernel driver name, admission function, BAR, DMA bits, integrated flag, chip
and memory queries, Metal admission, Vulkan driver entry point). This is why
an Intel backend is a data + compiler-target problem, not a rewrite.

## 4. Shader path

```
Metal library (.metallib)
  └─ metal/library.rs      parse the archive, keep original AIR + metadata
      └─ metal/compiler.rs AIR → NIR (C: src/compiler/air_to_nir.c, air_calls.c)
          └─ vendor NIR backend, linked in the image:
               NVIDIA → NAK   (Mesa src/nouveau/compiler)
               AMD    → ACO   (Mesa src/amd/compiler)
               INTEL  → BRW   (Mesa src/intel/compiler)   ← target for this port
```

AIR→NIR is shared and vendor-neutral, which is the single most important
reusable asset for Intel: only the NIR→machine-code backend changes.

## 5. Vendor-specific code (what an Intel port must touch)

NVIDIA-only today:
- `crates/stela-driver-gpu/src/nouveau_chip.rs`, `gsp_perf.rs`, `cold.rs`,
  `build/nouveau.rs`, `build/nouveau_firmware.rs`, `src/metal/nvidia.rs`
- `crates/stela-loader/.../recipes/nvidia_chip.rs` (chip naming)
- `crates/stela-cli/src/setup/firmware/nvidia.rs` (firmware download at install)
- `crates/stela-boot-core/src/gpu_status.rs` (all refusal text is NVIDIA-shaped)
- `crates/stela-boot/Cargo.toml`: `stela-drivers` is pulled with
  `features = ["native-acpi", "nouveau-port"]` — **no `xe-port`**

Intel pieces already present (upstream, mid-flight):
- `crates/stela-driver-gpu/build/xe.rs` — compiles unchanged xe + shared i915
  display code, generates the platform tables (`xe_devices.rs`)
- `crates/stela-driver-gpu/src/xe.rs` — admission by xe's own PCI ID table,
  DMA mask, platform name/display/discrete, `DRM_IOCTL_XE_DEVICE_QUERY` for
  chip ID and memory
- `crates/stela-driver-gpu/src/metal/intel.rs` — ANV admission, ISL linear
  alignment, sparse block size, and the ANV ICD entry point
- `crates/stela-driver-gpu/src/stack.rs` — `INTEL` stack, with
  `vulkan: None` ("ANV has run on no Intel GPU under Stela")
- `xtask/src/gpu/nvk.rs` — ANV is one of the three drivers the image may link
- `xtask/src/gpu/anv.rs` — host test that builds ANV and runs a BRW compute
  dispatch on a no-op xe shim
- `crates/stela-loader` — GuC/HuC/GSC/DMC firmware recipes, Tiger Lake →
  Panther Lake, by PCI device ID
- OpRegion / VBT reader (`stela-boot-core`) with no caller yet

## 6. Memory model

- No VRAM assumptions: `xe::query::memory_bytes` reports VRAM regions, else
  the system-memory region an integrated GPU allocates from.
- `Kernel::dma_bits` bounds every mapping; a mapping past the mask is
  refused, not truncated.
- Guest and host share one physical address space (`stela-driver-base::bus::dma`);
  the Metal layer pins pages rather than copying where it can.
- The image ships LLVM, Mesa and the translator in one EFI binary, so RSS is
  dominated by code + shader caches, not by a second OS.

## 7. Design rules the code enforces

- A stack whose `vulkan` is `None` still binds its kernel driver and can
  *display* frames another GPU drew; it never silently claims acceleration
  (`GpuStack::draws`).
- Capabilities are the conjunction of Vulkan features, compiled shader
  constructs and implemented API paths; every refusal is recorded as a `Gap`
  naming the missing layer.
- `Adapter::unavailable_reason` gives a user-readable reason per vendor; the
  Intel text already says i915 (pre-Tiger-Lake) is missing, not xe.
